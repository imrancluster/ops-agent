# M01: The LLM Client (my notes)

**One-line summary:** one neutral message format inside the agent; every provider is translated to and from it at the edge.

---

## Task 1: Neutral types (`internal/llm/types.go`)

- **Typed string constants** (`StopToolUse StopReason = "tool_use"`): a typo becomes a
  compile error instead of a silent runtime bug. The JSON is still a plain string.
- **Struct tags** (`json:"tool_use_id,omitzero"`): the JSON name + options.
  - json/v2 matches names **case-sensitively** when decoding: a wrong tag = a field that silently stays empty.
  - `omitzero` leaves a field out when it is `""`, `0`, `false` or `nil`. Use it for fields that
    only *some* blocks have (`id`, `is_error`, ...). Never on fields every block needs (`type`).
- **`jsontext.Value`** = raw JSON bytes we pass through without decoding (tool input: its shape depends on the tool).
- **Golden file** = a stored "known correct" output. The test compares against it, so the
  expected JSON is readable on its own and reviewable in a PR.
- **Decide by type, not by coincidence.** My first `Text()` appended `Text` from every block and
  passed the tests only because `tool_use` blocks had empty `Text`. A `thinking` block would have
  leaked the model's hidden reasoning to the user.
  **A passing test does not prove correct code: tests have gaps too.**
- **Library code doesn't log.** `internal/llm` returns values and errors; the caller decides what to log.

## Task 2: `APIError` (`internal/llm/errors.go`)

- **Typed error + `errors.As`**, never `strings.Contains(err.Error(), "429")`.
  The message is for humans and can change; the type and fields are the contract for code.
- `errors.As` finds the error **through every `%w` wrap**, so each layer can add context
  (`"agent step 2: send request: claude: HTTP 503"`) without hiding the original.
- **Why `Retryable()`, not `Temporary()`:** Go deprecated `net.Error.Temporary()` (Go 1.18) because
  "temporary" had no clear meaning. A name should describe the *decision the caller makes*:
  "should I retry?" → `Retryable`.
- **Retry rule:** 429 and 5xx = the server's problem, so wait and try again. Other 4xx = *our* request is
  wrong, so retrying sends the same mistake and burns money.
